# Enemy Forces 1.2.0：自动驾驶、战术终端与飞行视角修复

1.2.0 仍然**只改附属** `enemyforces`（modId `f16addon`），不改 SBW / DragonRise 的 jar。
战术终端相关的改动通过附属自带的客户端 Mixin（`f16addon.mixins.json`）作用在 SBW 的类上；
Mixin 配置为 `required: false`，SBW 将来改了内部实现时只会在日志里报错并跳过，不会导致崩溃。

---

## 1. 飞行时视角短暂失控（bug 修复）

### 根因

SBW 的 `ClientMouseHandler.handleClientTick` 每个客户端 tick 读取**鼠标绝对位置**，与上一 tick 相减得到位移
（夹在 ±256 px），再经过一个很慢的低通滤波（`lerpSpeedX/Y`，每 tick 系数 ≥ 0.12），作为摇杆量
`MouseMoveMessage` 发给服务器。但这个“绝对位置”本身是不连续的：

- 鼠标被锁定时，它是 GLFW 的无界虚拟坐标 `MouseHandler.xpos`；
- 有界面打开时，它是真实光标坐标，且 Minecraft 每次锁定/释放鼠标都会把光标重置到屏幕中心。

因此**打开或关闭任何界面**（战术终端、聊天、背包、暂停菜单、Alt-Tab 失焦再回来……）都会在一个 tick 内产生
最多 256 px 的“假位移”。界面打开期间 SBW 只发送 0 输入，但滤波器仍在吃光标在界面里的移动；界面一关，
累积值立刻发出并在 1–2 秒内缓慢衰减——飞机（以及绑定在飞机上的视角）自己俯仰/滚转，表现为
“视角短暂不受控制”。用 F-16 导弹锁定器在空中打开战术终端时尤其容易触发。

另外 SBW 的 `MouseHandlerMixin` 在机体有滚转时会混入**上一帧**的 Y 位移（`sbw$y`），界面期间该值不会更新，
关闭界面后的第一帧也会用到过期值。

### 修复

`client/FlightInputGuard`：在 SBW 处理器之前（同一 `ClientTickEvent.END`，`HIGHEST` 优先级）判断输入是否连续——
玩家存在、没有界面/覆盖层、鼠标被锁定、窗口有焦点、所乘载具没变。只要不连续，就：

- 把 `posN/posO` 重置为当前光标位置（下一次差值恰好为 0）；
- 清零 `speedX/Y`、`lerpSpeedX/Y`、`mouseXMoveTick/YMoveTick`、`lerpNacelleSpeedX/Y`；
- 清零 `MouseHandlerMixin` 的 `sbw$x / sbw$y`。

全部通过反射访问 SBW 的 `public static` 字段；若 SBW 改名，只记录一次警告并停用该守卫。

## 2. 单兵战术终端（雷达）卡顿

### 根因（按影响排序）

| # | 问题 | 影响 |
|---|---|---|
| 1 | `TacticalMapCache.periodicRescan` 每 250 ms 把最多 **512 个已绘制、未变化**的区块重新排队；`processChunkUpdates` 每 tick 最多重绘 256 个。每次重绘都重写 256 个像素、每像素分配 2 个 key、Deflate 压缩写盘队列、整张 256×256 贴图重新上传，并把覆盖它的所有 LOD 贴图作废（缩小视图时下一帧全部重建） | 地图打开期间持续掉帧，缩小视图时最严重 |
| 2 | 区块加载事件把 `LevelChunk` 整个放进队列，但**只有地图打开时才处理**。飞行几分钟后队列里是上千个已卸载区块（内存持续上涨），下次打开终端时按每 tick 256 个同步处理 | 打开终端时卡死数秒；飞行中 GC 压力 |
| 3 | 每 25 秒和关闭界面时，在渲染线程同步读取并重写磁盘缓存瓦片文件 | 周期性卡顿 |
| 4 | 导弹→目标的虚线由**每段 1 像素的 `fill`** 组成，在 1.20.1 中每个 `fill` 都是一次 draw call；每个实体图标是一次 `blit` | 导弹/实体多时每帧数百到上千次 draw call |
| 5 | `getWorldIdentifier()`（多人时做 SHA-256 + 格式化）在每个区块重绘时都被调用 | 小额但持续 |
| 6 | 打开地图后从磁盘恢复缓存区块：每 tick 最多 512（积压大时 ×4） | 首次打开时卡顿 |

### 修复（`mixin/TacticalMapCacheMixin`、`mixin/MapEntityRendererMixin`、`client/map/*`）

1. **变化检测**：重写 `updateChunk`，颜色/阴影算法与 SBW 完全一致（顶层非 NONE 地图色，水/岩浆，按上一列高度做明暗），
   但只写真正变化的像素；整块无变化时不标脏、不重传贴图、不作废 LOD、不写盘。
2. **刷新波次** 512 → 64 区块 / 250 ms（25×25 视野约 2.5 秒刷新一轮）。
3. **时间预算**：`processChunkUpdates` 改为按与视点距离取最近的 K 个（不再对整个队列排序），每 tick 最多 3 ms。
4. **后台消化**：`TacticalMapTicker` 在终端关闭时每 tick 用 1 ms 处理队列；区块卸载时立即绘制（每 tick 最多 24 个，其余丢弃），
   队列不再持有已卸载区块。
5. **异步写盘**：`MapDiskWriter` 单独的低优先级守护线程，文件格式不变，原子替换。
6. **LOD 作废节流**：最多每 750 ms 一次。
7. **磁盘恢复**：每 tick 最多 64 个区块。
8. **批量绘制**：`MapDraw` 把彩色几何（三角形）、按贴图分组的图标、文字合并为少量 draw call；虚线先裁剪到地图区域再分段。
9. 世界标识缓存 1 秒。

## 3. 战术终端 UI 表现力

都画在 SBW 原有地图上，原有交互（右键菜单、框选、导弹打击、标记、跟随）保持不变：

- **态势面板**（地图左侧原本空白的区域）：
  - 本机：载具名、高度/离地高度、速度 km/h、航向、结构完整度条；
  - **导弹告警**：锁定本机/本人的导弹数量、最近距离与方位（闪烁）；
  - 兵力统计：敌/友/中立/导弹；
  - **敌方接触列表**（由近到远，最多 12 条）：类型、名称、距离、方位、高度、接近/远离趋势；**点击条目把地图定位到该目标**。
- **接触符号**（参考 NTDS / MIL-STD-2525）：敌方菱形、友方圆形、中立方形外框；
- **速度矢量线**：显示 1.5 秒后的位置；
- 空中目标与导弹的**离地高度标签**；
- 锁定本机的导弹有**红色脉冲圈**，其目标线变红；
- **雷达扫描**：每个雷达扇区画出边界与来回扫描的波束（360° 雷达为旋转波束）和渐隐尾迹；
- **距离环**：以本机为中心，按缩放自动选择 50 m–20 km 间隔，带标注；本机航向线。

## 4. 敌方自动驾驶

### F-16（`F16FlightAI`）

仍是运动学飞控（`setPos`），SBW 物理不参与：

| 方面 | 1.1.0 | 1.2.0 |
|---|---|---|
| 地形 | 只探测前方一个点；来不及时每 tick 直接把飞机向上瞬移最多 0.9 格 | 沿**当前航向与指令航向**各探测 0.4/1/2 秒处的地形取最大值，提前抬头爬升；任何机动都不低于离地 10 格 |
| 转弯 | 固定偏航速率，滚转只是装饰 | **协调转弯**：先滚转（6°/tick，最大 65°），转弯速率随坡度增加 |
| 速度 | 固定巡航/战斗速度 | 能量管理：急转掉速，俯冲加速，爬升减速 |
| 导弹规避 | 只有干扰弹 | 被锁定且导弹在 `evasionRange`（默认 320 格）内并接近时，做**侧置机动（beam，转到与导弹视线垂直的方向）**+ 下降 + 全速，同时继续放干扰弹 |
| 空战 | 瞄准目标 + 固定 10 tick 提前量 | 按距离比例的**提前量追踪**；目标在后方且很近时先**脱离拉开**再回头 |
| 对地 | 在目标上方 42 格绕圈飞 | **攻击航线**：进入（离地约 70 格）→ 对准后俯冲 → 低于 30 格或接近 70 格时拉起 → 飞越脱离 420 格 → 回转再次进入 |
| 编队 | 同时起飞的飞机会重叠 | 互相保持约 40 格间隔 |
| 模拟区边缘 | 前方 48 格（不到转弯半径一半）才检测，飞到边界时悬停在半空 | 前方 0.5/0.9 个**转弯半径**检测，提前转向最近的玩家（模拟区中心），**不丢失当前目标** |
| 目标速度 | 读 `getDeltaMovement()`；玩家驾驶的 SBW 载具在服务端通常为 0，提前量实际无效 | 每 tick 测量目标位移并平滑，用于追踪与机炮提前量 |
| 起飞 | 原地垂直上升 | 沿跑道方向加速爬升；前方有坡则加大爬升角，前方有山才退回垂直爬升 |

### 地面单位（`GroundUnitAI`）

- **扇形探路**：每 10 tick 在目标方向 ±115° 内 9 个候选方向各探测 7 格，排除高于一步（1.25 格）的墙、超过 4 格的落差、
  水/岩浆（`avoidWater`）和模拟区外，选最接近目标方向的可行路线；绕障时保持同一侧，不来回摆。
- 航向偏差大时**原地转向**，不再朝错误方向开出去。
- **卡住处理**：连续受阻 20 tick 倒车 25 tick 并换另一侧绕行；60 tick 仍不行则换巡逻点。
- 驾驶时也不会开进水里、不会从 4 格以上的悬崖开下去。
- 静止交战时车体正面朝向敌人；**失去视线 20 tick** 后越过正常对峙距离继续抵近（最近 16 格）寻找射击位置。

### 服务端区块查询不再阻塞

`WorldQueries` 的地形/视线/流体查询全部改为 `getChunkNow()`（详见第 5 节）。

### 新增配置（`serverconfig/f16addon-server.toml`）

```toml
[f16]
	minGroundClearance = 50.0   # 巡航离地高度；空战 80%，俯冲攻击最低 30 格，任何情况不低于 10 格
	evasiveManeuvers = true     # 被导弹锁定时做 beam 机动
	evasionRange = 320.0        # 触发规避的导弹距离

[ground]
	avoidWater = true           # 地面单位绕开水/岩浆
```

## 5. 验证

### 服务端实测（Forge 1.20.1-47.4.0 专用服，无玩家，普通地形种子 `20261114`）

场景：forceload 32×32 区块；蓝队 6 架悬停 AH-6 + 4 辆 T-90A（加入计分板队伍 `blue`）；敌方 3 架 F-16、3 辆 T-80、
2 辆 BMPT-72、1 套黄蜂，相距约 200 格。部署后每 10 秒取一次 `/f16addon perf` 与 `/forge tps`，共 120 秒。

| | 1.1.0 | 1.2.0（初版） | 1.2.0（最终） |
|---|---|---|---|
| AI 平均 ms/tick（12 次采样） | 0.09–0.50 | 0.09–23.3 | 0.04–0.36 |
| AI 单 tick 最大 | 104 ms | **2276 ms** | 101 ms（后半程 2–4 ms） |
| JFR：附属代码中的线程阻塞（`ThreadPark`） | 0 | 57.6 ms × 多次 | **0** |
| 刷在水里的 T-80 | 全程卡住 | 全程卡住 | 驶出水面并推进到目标附近 |
| 其他地面单位 | 两辆开在水面上（y=63） | — | 均在陆地上推进到目标 |

“初版”的秒级尖峰来自一个 1.1.0 就存在的隐患：`WorldQueries` 用 `hasChunk()` 判断区块可用，但在服务端它只表示
“区块被票据保持在 FULL 级别”，**区块可能仍在生成**，随后的 `getHeight()` 会让主线程等待生成完成。1.2.0 新增的多点地形
探测更容易碰到正在生成的区块，把问题放大了。现在所有查询都改用只返回已完成区块的 `getChunkNow()`
（JFR 确认附属代码中不再有任何阻塞）。这同样修复了玩家在视距边缘飞行时偶发的服务端卡顿。

两版的峰值几十毫秒属于同一来源（AI 回调中 SBW 自身的弹体生成逻辑与 GC），量级相当。

### 客户端

当前环境没有图形界面，**无法实际启动客户端**，因此客户端改动（视角守卫、战术终端 Mixin 与 UI）只做了：

- 编译 + reobf 通过；
- 用 ASM 写的静态校验器核对 reobf 后 jar：每个 `@Shadow` 字段/方法、`@Inject` 目标方法与参数签名、
  `@ModifyConstant` 常量（`512` 在 `periodicRescan` 中恰好出现 1 次）都与 SBW 0.8.9.2 字节码一致；所有 MC 成员引用都已映射为 SRG 名；
- 地图着色逻辑逐行对照 SBW 反编译结果复刻（含 SRG→官方名核对：流体分支是 `LAVA → COLOR_ORANGE`，否则 `WATER`）。

建议进游戏重点确认：空中打开/关闭战术终端后飞机不再自己机动；终端打开、平移、缩放时的帧率；态势面板与地图符号显示。
Mixin 配置为非必需（`required: false`），若某个注入失败只会在日志里出现 `f16addon.mixins.json` 相关错误，不会崩溃。

## 6. 构建

```bash
cd addon-src
./gradlew build          # build/libs/enemyforces-1.2.0.jar（已 reobf）
```

`build.gradle` 现在把 `../mods/` 里的 SBW jar 作为 `compileOnly` 依赖（只供客户端 Mixin 编译；SBW jar 本身已是 SRG 名，
因此所有 Mixin 都是 `remap = false`，无需 refmap）。服务端 AI 仍通过缓存反射调用 SBW。
